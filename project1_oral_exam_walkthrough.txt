==================================================
MapReduce core idea (very important)
==================================================
- `key` = grouping bucket.
- `value` = information carried for that bucket.
- Hadoop sends all records with same key to one reducer call.
- So key choice controls correctness and performance.

Example:
- If mapper emits `(hobby, 1)`, reducer sees one hobby at a time with many 1s.
- If mapper emits `(Null, row)`, all rows go to one reducer bucket.
- `Null` is used when we need a global operation (like top-10 over all rows).

==================================================
Why we introduced caching (Distributed Cache)
==================================================
How we reached it:
1) Built correct baseline solutions first (often reduce-side join).
2) Noticed some stages only did lookup enrichment (nickname, region, counts).
3) Tried distributed cache to copy smaller lookup table to each worker.
4) This removed extra MR stage in some optimized versions.

Why it looked useful:
- fewer job stages
- less shuffle in some cases
- simpler map-side lookup logic

Important limitation:
- Works only when cached lookup table is small enough for memory.
- For large lookup tables, reduce-side joins are safer.
- Professor comments correctly identify these limits in D/F/G/H.

TASK A: Frequency of each FavoriteHobby
==================================================
What task means
- Count number of users for each hobby.

Key-value mapping and meaning
- Mapper: `(FavoriteHobby, 1)`
  - key means "group by hobby"
  - value 1 means "one user row"
- Reducer: `(FavoriteHobby, totalCount)`

Simple solution flow
1) Read each CircleNetPage row.
2) Extract hobby.
3) Emit `(hobby, 1)`.
4) Reducer sums all 1s per hobby.

Optimized solution flow (implemented)
1) Same mapper and reducer.
2) Add combiner (same sum logic).
3) Local partial sums happen before shuffle.
4) Network I/O reduces.

Why chosen
- This is textbook group-by count.

Self-evaluation
- Strong, correct, scalable.

TASK B: Top 10 most popular pages (ID, NickName, JobTitle)
==================================================
What task means
- Find pages with highest access counts from ActivityLog.
- Return page ID + NickName + JobTitle.

Simple solution (3 jobs)
Job1: count page accesses
- Mapper: `(WhatPage, 1)`
  - key groups all accesses for same page
  - value 1 means one access event
- Reducer: `(PageID, accessCount)`

Job2: join counts with page metadata
- Page mapper: `(PageID, "P,Nick,Job")`
  - `P` tag marks page-metadata record
- Count mapper: `(PageID, "C,count")`
  - `C` tag marks count record
- Reducer receives one PageID bucket and merges P + C
- Output row has id, nick, job, count

Job3: global top 10
- Mapper emits `(Null, row)` for each row
  - `Null` key means one shared bucket for all rows
- Reducer sees all rows globally, keeps best 10 by count

Optimized solution (2 jobs)
Job1
- Same count stage with combiner.

Job2
- Mapper emits `(Null, "PageID\tcount")`
- Single reducer computes top 10
- Reducer loads CircleNetPage via distributed cache to attach nick/job

Why chosen
- Need count + metadata + global ranking.
- Optimized version removes one full join stage.

Scale risk
- Cache join depends on page table fitting memory.

TASK D: Popularity factor (followers per owner, include zero)
==================================================
What task means
- For every page owner, report nickname and follower count.
- Owners with zero followers must appear.

Simple solution (reduce-side join)
- Page mapper: `(OwnerID, "P,Nick")`
- Follows mapper: `(FollowedID, "F,1")`
- Reducer for each OwnerID:
  - gets nick from P record
  - sums F records to follower count
  - outputs zero if no F records

Key-value meaning
- key `OwnerID` groups page info + follower signals for same owner
- values are tagged payloads (`P` or `F`)

Optimized solution (2 jobs)
Job1: follower counting
- Mapper `(FollowedID, 1)` -> Reducer `(OwnerID, followerCount)`

Job2: map-side join
- Mapper scans pages and loads counts from cache
- emits final `(ID,Nick,countOrZero)` row

Professor comment
- Correct: optimized code uses only `part-r-00000` from job1.
- Not robust if job1 has multiple reducers.

Safer large-scale options
- read all `part-r-*` files
- or keep reduce-side join
- or force one reducer intentionally (small/controlled runs)

TASK E: Total actions and distinct pages per owner
==================================================
What task means
- For each owner ID:
  - total number of actions they performed
  - number of distinct pages they visited

Implemented mapping
- PageOwner mapper: `(OwnerID, "P,1")`
  - `P` means this ID is a valid owner
- Activity mapper: `(ByWho, "A,WhatPage")`
  - `A` means activity record, WhatPage needed for distinct counting

Reducer output
- `(OwnerID, "totalActions,distinctPages")`

Simple flow
1) Reducer gets one owner bucket.
2) If `P` exists, keep owner.
3) Count all A records as total actions.
4) Add WhatPage to set for distinct count.

Optimized solution status
- In current source, TaskE is only simple (no separate TaskEOptimized in `src`).

Scale risk
- Very active users may create big in-memory distinct sets.

TASK F: Owners above average follower count
==================================================
What task means
- Compute average followers across all owners.
- Output owners whose follower count > average.

Simple solution (3 jobs)
Job1: owner counts
- Page mapper `(OwnerID, "P,Nick")`
- Follow mapper `(FollowedID, "F,1")`
- Reducer outputs owner rows with count

Job2: average
- Mapper emits `("avg", count)`
  - key `avg` puts all counts in one reducer bucket
- Reducer computes global average

Job3: filter
- Mapper compares count > avg and emits qualifying rows
- Reducer pass-through

Optimized solution (2 jobs)
Job1
- Count followers `(FollowedID, 1)` -> `(OwnerID, followerCount)`

Job2
- Driver reads job1 output + total page count to compute avg
- Mapper loads counts from cache and scans pages
- Emits owners above avg

Professor comment
- Correct: optimized code reads only `part-r-00000` from job1.
- Multi-reducer outputs can make avg wrong.

Safer options
- aggregate all part files
- or compute average in dedicated MR aggregation stage

TASK G: Outdated pages (no access in last 90 days)
==================================================
What task means
- Outdated if user last access < (global latest access - 2160 hours).
- 2160 = 90 days * 24 hours/day.

Simple solution (3 jobs)
Job1: global max time
- Mapper `(Null, ActionTime)`
- Reducer outputs one global max

Job2: per-user max time
- Mapper `(ByWho, ActionTime)`
- Reducer outputs `(UserID, userMaxTime)`

Job3: join pages + user max and filter
- Page mapper `(UserID, "P,Nick")`
- UserMax mapper `(UserID, "M,userMax")`
- Reducer compares threshold and outputs outdated users

Meaning of keys
- `Null` in Job1 means all times in one global bucket
- `UserID` in Job2/Job3 means per-user grouping

Optimized solution (2 jobs)
Job1
- Per-user max `(ByWho, ActionTime)` -> `(UserID, userMaxTime)`

Job2
- Driver reads job1 output for global max
- Mapper loads user-max cache and scans pages
- Emits outdated users

Professor comment
- Correct: optimized code assumes one output part (`part-r-00000`).

Safer options
- read all parts
- or dedicated global-max MR stage
- or force one reducer when justified

TASK H: Same-region one-way follows (not followed back)
==================================================
What task means
- Find users who follow someone in same region but are not followed back.
- Output ID and nickname.

Simple solution (2 jobs)
Job1: same-region asymmetry detection
- Mapper loads region map from cache
- For edge A->B in same region emits:
  - key `(min(A,B), max(A,B))`
  - value `A->B`
- Why this key:
  - both directions between same pair go to one reducer bucket
- Reducer checks:
  - both directions present => symmetric
  - only one direction => one-way, output follower ID

Job2: attach nickname
- Follower mapper `(ID, "F")`
- Page mapper `(ID, "P,Nick")`
- Reducer joins and outputs `(ID,Nick)`

Optimized solution (1 job)
- Mapper (with cached regions) emits:
  - `(A, "O,B")` outgoing marker
  - `(B, "I,A")` incoming marker
- Reducer for user U builds outgoing/incoming sets
- If any outgoing target missing in incoming set => one-way exists
- Reducer loads nickname map from cache and outputs `(U, nick)`

Professor comment
- Correct: full CircleNetPage caching can fail at large scale.

Safer option
- reduce-side joins with CircleNetPage instead of full-table memory cache

Detailed oral-answer explanations (ready to speak)
==================================================
Task A (detailed explanation)
- In Task A, the question is purely a grouped count: "for each hobby, how many users have it?" That is why hobby is the key. When mapper emits `(hobby, 1)`, it is saying "this user belongs to hobby bucket X and contributes one count." Hadoop automatically gathers all values with the same hobby key at reducer side, and reducer simply adds them. This is exactly the kind of job where MapReduce is strongest: simple local extraction in mapper and grouped aggregation in reducer. In optimized mode, we added combiner using the same sum logic, so each mapper sends smaller partial totals instead of many 1s, which reduces shuffle traffic. This optimization is safe because summation order does not change final result.

Task B (detailed explanation)
- Task B has two logical parts: first calculate popularity (access counts), then attach page identity fields and keep only top-10 globally. In simple mode we use three jobs because each job has one clear purpose. Job1 uses key `WhatPage` and value `1`, so reducer gets all visits of same page and returns accessCount. Job2 performs a join keyed by PageID: page stream emits tagged values `P,Nick,Job` and count stream emits `C,count`; reducer merges these tags for the same key. Job3 computes true global top-10 by forcing all rows into one bucket with `Null` key. `Null` does not mean missing data; it means deliberate "single bucket" routing so one reducer can compare all candidates globally. In optimized mode, we still count first, then use one reducer for top-10 and load page metadata from cache to avoid one full join stage. This is faster locally but depends on metadata table size.

Task C (detailed explanation)
- Task C is conceptually simple filtering: return users whose hobby equals selected target. Implemented mapper checks hobby and emits `(NickName, JobTitle)` for matching rows. In current code a reducer exists, but it only passes records through. So current implementation is correct in output, but not efficient in execution because reducer introduces shuffle and sorting without adding business logic. The better design is map-only: same mapper, no reducer, `setNumReduceTasks(0)`. This is a good oral point because it shows you understand the difference between correctness and efficiency. Professor comment is fully valid here.

Task D (detailed explanation)
- Task D asks for follower count per owner, including owners with zero followers. That "including zero" is important because it requires starting from the full owner list, not only from follows table. In simple design, we use OwnerID as join key with two tagged streams: page stream `P,Nick` and follows stream `F,1` keyed by followed user ID. Reducer receives both kinds for same OwnerID, extracts nickname from P and sums all F values. If no F exists but P exists, count remains zero, which satisfies requirement. In optimized design, Job1 first computes follower counts only, then Job2 map-joins those counts into pages using distributed cache. This reduces one heavy join stage. However, professor comment is correct: current optimized code loads only `part-r-00000`; if Job1 has multiple reducer outputs, results become incomplete. So scalability fix is reading all part files or using robust reduce-side join.

Task E (detailed explanation)
- Task E needs two metrics per owner: total actions and distinct pages accessed. We key by owner/user ID so all records for one user arrive together. PageOwner mapper emits `P,1` as an ownership marker; Activity mapper emits `A,WhatPage` as action payload. Reducer logic is: confirm owner exists (P marker), increment total for every A record, and place WhatPage in a set for distinct counting. Final output is `(OwnerID, totalActions, distinctPages)`. This design is compact and easy to defend because one reducer pass computes both metrics consistently. The only scalability caveat is memory pressure for extremely active users due to large distinct sets, but for project scale this is acceptable.

Task F (detailed explanation)
- Task F is a threshold query where threshold is global average followers. Because the threshold depends on full dataset, we need a global aggregation step before final filtering. In simple path, Job1 builds owner follower counts; Job2 computes average by mapping each count under single key `avg`, which intentionally sends all counts to one reducer to compute one scalar average; Job3 filters owner rows above that scalar. In optimized path, we count followers first, compute average in driver by reading intermediate data, then map-side filter pages using cached counts. This reduces stages but introduces sensitivity to how intermediate files are read. Professor comment is correct: relying on one output part (`part-r-00000`) is not cluster-robust. Production-safe approach must aggregate all output partitions or keep full MR aggregation.

Task G (detailed explanation)
- Task G defines outdated users relative to latest observed activity time, not fixed wall-clock date. So algorithm needs two maxima: global max activity time and per-user max activity time. In simple mode, Job1 computes global max using `Null` key so all times are compared together; Job2 computes user max using key `ByWho`; Job3 joins user max with page list and applies threshold `(globalMax - 2160)` where 2160 is 90 days in hours. Users with missing activity are also outdated. Optimized mode skips explicit global-max job by reading user-max output in driver and deriving global max there, then filtering pages with cached user-max table. This is faster in small setups but professor comment is valid: reading only one part file can miss data if outputs are partitioned.

Task H (detailed explanation)
- Task H asks for one-way follows inside same region. There are two checks: region equality and reciprocity failure. In simple mode, mapper first filters follows edges using cached region lookup; for each valid edge A->B it emits pair key `(min(A,B), max(A,B))` and value `A->B`. This key design ensures both directions for same pair land in one reducer call, letting reducer detect whether both directions exist (symmetric) or only one (one-way). Then second job joins flagged IDs with page table to attach nicknames. Optimized mode compresses to one job by emitting outgoing markers `O,*` and incoming markers `I,*` per user and checking set difference in reducer; nickname is loaded from cache for output. This works for moderate data, but professor comment is correct that full page-table caching (region + nick maps) is not scalable for very large tables.

Detailed final defense statement
- Our implementations are functionally correct for course-scale runs. We intentionally developed both simple and optimized variants to compare clarity and performance. The key technical maturity point is that we can now separate "works correctly" from "scales safely": map-only should replace pass-through reducers, global metrics must avoid single-part assumptions, and distributed cache should be used only when lookup data is small enough. This balanced explanation is usually strong in oral examinations.
