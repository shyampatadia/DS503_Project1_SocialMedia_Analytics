How we "discovered" caching (Distributed Cache)
==================================================
Simple story you can tell in oral exam
- First we built correct solutions using normal reduce-side join.
- Then we saw some jobs are doing extra shuffle/join just to add small lookup info (nickname, region, count table).
- So we asked: if lookup table is small, can we copy it to each worker and avoid one full join stage?
- Hadoop gives this feature: distributed cache.
- We tested it and it was faster in pseudo-distributed environment.

Why we thought it is useful
- Fewer jobs in some tasks.
- Less network shuffle in some stages.
- Cleaner map-side lookup logic.

Very important limitation
- This only works well when cached file is small enough for memory.
- For very large files, this is not scalable.
- Professor comments are correct where they point this out.

One-line oral answer
- "We used caching as an optimization after building correct baseline joins. It improved local performance, but we understand its memory limits at cluster scale."

Task A: Frequency of each hobby
==================================================
What it means
- Count how many users have each FavoriteHobby.

Key-value mapping
- Mapper output: (FavoriteHobby, 1)
- Reducer output: (FavoriteHobby, totalCount)

Simple solution
- One job.
- Mapper reads hobby from page row and emits 1.
- Reducer sums all 1 values for each hobby.

Optimized solution (YES, implemented)
- Same logic as simple.
- Adds combiner with same sum function.
- Combiner does local partial sum before shuffle.

Why this is good
- Counting by key is a perfect MapReduce use case.
- Combiner is safe because sum can be merged in any order.

Weak point
- No major weak point here. This is already scalable.

==================================================
What it means
- Find pages with highest access count in ActivityLog.

Key-value mapping
Simple (3 jobs)

- Job2 count map: (PageID, "C,count")

- Job3 reduce output: top 10 rows

- Job1: same counting with combiner

Why we chose this

- Optimized version removes one full join stage.

Weak point

Task H: Same-region one-way follows (not followed back)
==================================================
What it means
- Find users who follow someone in same region, but that person does not follow back.
- Output ID and nickname.

Key-value mapping
Simple (2 jobs)
- Job1 mapper (cached region map): ("minID,maxID", "A->B")
- Job1 reducer: if only one direction exists, output (followerID, "F")
- Job2 follower mapper: (ID, "F")
- Job2 page mapper: (ID, "P,Nick")
- Job2 reducer: output (Null, "ID,Nick")

Optimized (1 job)
- Mapper emits two records per same-region edge:
- (A, "O,B") outgoing
- (B, "I,A") incoming
- Reducer compares outgoing set and incoming set
- If one-way exists, reducer outputs user with nick (nick loaded from cache)

Why we chose this
- Tried to merge logic into one job for speed.

Professor comment
- Full CircleNetPage in distributed cache does not scale.

Evaluation
- Correct comment.
- Region + nickname maps are loaded in memory; risky for large table.

Safer large-scale option
- Use reduce-side joins with CircleNetPage instead of full table cache.
