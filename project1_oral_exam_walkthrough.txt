==================================================
MapReduce core idea (very important)
==================================================
- `key` = grouping bucket.
- `value` = information carried for that bucket.
- Hadoop sends all records with same key to one reducer call.
- So key choice controls correctness and performance.

Example:
- If mapper emits `(hobby, 1)`, reducer sees one hobby at a time with many 1s.
- If mapper emits `(Null, row)`, all rows go to one reducer bucket.
- `Null` is used when we need a global operation (like top-10 over all rows).

==================================================
Why we introduced caching (Distributed Cache)
==================================================
How we reached it:
1) Built correct baseline solutions first (often reduce-side join).
2) Noticed some stages only did lookup enrichment (nickname, region, counts).
3) Tried distributed cache to copy smaller lookup table to each worker.
4) This removed extra MR stage in some optimized versions.

Why it looked useful:
- fewer job stages
- less shuffle in some cases
- simpler map-side lookup logic

Important limitation:
- Works only when cached lookup table is small enough for memory.
- For large lookup tables, reduce-side joins are safer.
- Professor comments correctly identify these limits in D/F/G/H.

TASK A: Frequency of each FavoriteHobby
==================================================
What task means
- Count number of users for each hobby.

Key-value mapping and meaning
- Mapper: `(FavoriteHobby, 1)`
  - key means "group by hobby"
  - value 1 means "one user row"
- Reducer: `(FavoriteHobby, totalCount)`

Simple solution flow
1) Read each CircleNetPage row.
2) Extract hobby.
3) Emit `(hobby, 1)`.
4) Reducer sums all 1s per hobby.

Optimized solution flow (implemented)
1) Same mapper and reducer.
2) Add combiner (same sum logic).
3) Local partial sums happen before shuffle.
4) Network I/O reduces.

Why chosen
- This is textbook group-by count.

Self-evaluation
- Strong, correct, scalable.

TASK B: Top 10 most popular pages (ID, NickName, JobTitle)
==================================================
What task means
- Find pages with highest access counts from ActivityLog.
- Return page ID + NickName + JobTitle.

Simple solution (3 jobs)
Job1: count page accesses
- Mapper: `(WhatPage, 1)`
  - key groups all accesses for same page
  - value 1 means one access event
- Reducer: `(PageID, accessCount)`

Job2: join counts with page metadata
- Page mapper: `(PageID, "P,Nick,Job")`
  - `P` tag marks page-metadata record
- Count mapper: `(PageID, "C,count")`
  - `C` tag marks count record
- Reducer receives one PageID bucket and merges P + C
- Output row has id, nick, job, count

Job3: global top 10
- Mapper emits `(Null, row)` for each row
  - `Null` key means one shared bucket for all rows
- Reducer sees all rows globally, keeps best 10 by count

Optimized solution (2 jobs)
Job1
- Same count stage with combiner.

Job2
- Mapper emits `(Null, "PageID\tcount")`
- Single reducer computes top 10
- Reducer loads CircleNetPage via distributed cache to attach nick/job

Why chosen
- Need count + metadata + global ranking.
- Optimized version removes one full join stage.

Scale risk
- Cache join depends on page table fitting memory.

TASK D: Popularity factor (followers per owner, include zero)
==================================================
What task means
- For every page owner, report nickname and follower count.
- Owners with zero followers must appear.

Simple solution (reduce-side join)
- Page mapper: `(OwnerID, "P,Nick")`
- Follows mapper: `(FollowedID, "F,1")`
- Reducer for each OwnerID:
  - gets nick from P record
  - sums F records to follower count
  - outputs zero if no F records

Key-value meaning
- key `OwnerID` groups page info + follower signals for same owner
- values are tagged payloads (`P` or `F`)

Optimized solution (2 jobs)
Job1: follower counting
- Mapper `(FollowedID, 1)` -> Reducer `(OwnerID, followerCount)`

Job2: map-side join
- Mapper scans pages and loads counts from cache
- emits final `(ID,Nick,countOrZero)` row

Professor comment
- Correct: optimized code uses only `part-r-00000` from job1.
- Not robust if job1 has multiple reducers.

Safer large-scale options
- read all `part-r-*` files
- or keep reduce-side join
- or force one reducer intentionally (small/controlled runs)

TASK E: Total actions and distinct pages per owner
==================================================
What task means
- For each owner ID:
  - total number of actions they performed
  - number of distinct pages they visited

Implemented mapping
- PageOwner mapper: `(OwnerID, "P,1")`
  - `P` means this ID is a valid owner
- Activity mapper: `(ByWho, "A,WhatPage")`
  - `A` means activity record, WhatPage needed for distinct counting

Reducer output
- `(OwnerID, "totalActions,distinctPages")`

Simple flow
1) Reducer gets one owner bucket.
2) If `P` exists, keep owner.
3) Count all A records as total actions.
4) Add WhatPage to set for distinct count.

Optimized solution status
- In current source, TaskE is only simple (no separate TaskEOptimized in `src`).

Scale risk
- Very active users may create big in-memory distinct sets.

TASK F: Owners above average follower count
==================================================
What task means
- Compute average followers across all owners.
- Output owners whose follower count > average.

Simple solution (3 jobs)
Job1: owner counts
- Page mapper `(OwnerID, "P,Nick")`
- Follow mapper `(FollowedID, "F,1")`
- Reducer outputs owner rows with count

Job2: average
- Mapper emits `("avg", count)`
  - key `avg` puts all counts in one reducer bucket
- Reducer computes global average

Job3: filter
- Mapper compares count > avg and emits qualifying rows
- Reducer pass-through

Optimized solution (2 jobs)
Job1
- Count followers `(FollowedID, 1)` -> `(OwnerID, followerCount)`

Job2
- Driver reads job1 output + total page count to compute avg
- Mapper loads counts from cache and scans pages
- Emits owners above avg

Professor comment
- Correct: optimized code reads only `part-r-00000` from job1.
- Multi-reducer outputs can make avg wrong.

Safer options
- aggregate all part files
- or compute average in dedicated MR aggregation stage

TASK G: Outdated pages (no access in last 90 days)
==================================================
What task means
- Outdated if user last access < (global latest access - 2160 hours).
- 2160 = 90 days * 24 hours/day.

Simple solution (3 jobs)
Job1: global max time
- Mapper `(Null, ActionTime)`
- Reducer outputs one global max

Job2: per-user max time
- Mapper `(ByWho, ActionTime)`
- Reducer outputs `(UserID, userMaxTime)`

Job3: join pages + user max and filter
- Page mapper `(UserID, "P,Nick")`
- UserMax mapper `(UserID, "M,userMax")`
- Reducer compares threshold and outputs outdated users

Meaning of keys
- `Null` in Job1 means all times in one global bucket
- `UserID` in Job2/Job3 means per-user grouping

Optimized solution (2 jobs)
Job1
- Per-user max `(ByWho, ActionTime)` -> `(UserID, userMaxTime)`

Job2
- Driver reads job1 output for global max
- Mapper loads user-max cache and scans pages
- Emits outdated users

Professor comment
- Correct: optimized code assumes one output part (`part-r-00000`).

Safer options
- read all parts
- or dedicated global-max MR stage
- or force one reducer when justified

TASK H: Same-region one-way follows (not followed back)
==================================================
What task means
- Find users who follow someone in same region but are not followed back.
- Output ID and nickname.

Simple solution (2 jobs)
Job1: same-region asymmetry detection
- Mapper loads region map from cache
- For edge A->B in same region emits:
  - key `(min(A,B), max(A,B))`
  - value `A->B`
- Why this key:
  - both directions between same pair go to one reducer bucket
- Reducer checks:
  - both directions present => symmetric
  - only one direction => one-way, output follower ID

Job2: attach nickname
- Follower mapper `(ID, "F")`
- Page mapper `(ID, "P,Nick")`
- Reducer joins and outputs `(ID,Nick)`

Optimized solution (1 job)
- Mapper (with cached regions) emits:
  - `(A, "O,B")` outgoing marker
  - `(B, "I,A")` incoming marker
- Reducer for user U builds outgoing/incoming sets
- If any outgoing target missing in incoming set => one-way exists
- Reducer loads nickname map from cache and outputs `(U, nick)`

Professor comment
- Correct: full CircleNetPage caching can fail at large scale.

Safer option
- reduce-side joins with CircleNetPage instead of full-table memory cache

Short oral-answer paragraphs (ready to speak)
==================================================
Task A
- We grouped by hobby because question is per-hobby count. Mapper emits `(hobby,1)` and reducer sums. Optimized version adds combiner for local partial sums, reducing shuffle without changing correctness.

Task B
- We first count accesses per page, then attach metadata, then compute global top-10. `Null` key in final stage means all rows go to one reducer so ranking is truly global. Optimized version merges top-10 and metadata join using cache.

Task C
- It is a filter problem, so mapper emits only matching `(NickName,JobTitle)` rows. Current reducer is pass-through and not needed. Best config is map-only with zero reducers.

Task D
- We used owner ID as join key so page info and follower signals meet in same reducer. That gives follower count including zeros. Optimized map-side join works locally but currently assumes single reducer output file.

Task E
- We grouped by owner ID and merged owner markers with activity markers. Reducer counts all actions and distinct pages together in one pass. This is correct and straightforward for current data size.

Task F
- We need a global average first, then filter. That is why simple version uses multi-stage pipeline. Optimized version computes counts then filters via cached lookup, but reading only `part-r-00000` is a scalability risk.

Task G
- We compare each user’s latest activity to `globalMax-2160`. Simple version computes global max and user max explicitly. Optimized version reduces jobs but again assumes one output part when reading intermediate results.

Task H
- We detect one-way same-region follow relationships by grouping direction pairs together (simple) or outgoing/incoming sets per user (optimized). Cache helps speed, but full-page-table caching is not robust at larger scale.
