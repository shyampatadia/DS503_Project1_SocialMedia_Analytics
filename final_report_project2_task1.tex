    \section{Task 1: Pig Implementation}
    For Project 2 Task 1, We rewrote Project 1 analytics Tasks A--H in Apache Pig and tested them on the same CircleNet dataset from Project 1.
    The Pig scripts are saved inside the same task folders used for the Java MapReduce code:
    \begin{itemize}
        \item \texttt{src/main/java/circlenet/taskA/taskA.pig}
        \item \texttt{src/main/java/circlenet/taskB/taskB.pig}
        \item \texttt{src/main/java/circlenet/taskC/taskC.pig}
        \item \texttt{src/main/java/circlenet/taskD/taskD.pig}
        \item \texttt{src/main/java/circlenet/taskE/taskE.pig}
        \item \texttt{src/main/java/circlenet/taskF/taskF.pig}
        \item \texttt{src/main/java/circlenet/taskG/taskG.pig}
        \item \texttt{src/main/java/circlenet/taskH/taskH.pig}
    \end{itemize}

    We also recorded Pig timing in \texttt{pig\_task\_times.csv} and compared against the best MapReduce timings from Project 1 using \texttt{mr\_vs\_pig\_comparison.csv}.

    \subsection{Implementation Summary by Task (A--H)}

    \subsubsection*{Task A -- Frequency of FavoriteHobby}
    \textbf{Pig idea:} load pages, keep hobby field, group by hobby, count.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Loaded CircleNetPage with full schema.
        \item Created a cleaned hobby relation using \texttt{TRIM(...)} and removed null/empty hobby values.
        \item Grouped by hobby and counted rows in each group.
    \end{itemize}

    \textbf{Why this design:}
    This is a direct aggregation task. Pig handles it naturally with \texttt{GROUP + COUNT}.

    \subsubsection*{Task B -- Top 10 Most Accessed Pages}
    \textbf{Pig idea:} count accesses per page, join with page metadata, sort by count descending, limit 10.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Loaded ActivityLog and counted \texttt{whatpage} frequency.
        \item Joined counts with CircleNetPage (ID, nickname, job title).
        \item Ordered by access count descending and applied \texttt{LIMIT 10}.
    \end{itemize}

    \textbf{Why this design:}
    The task needs both aggregation and join. Pig relational operators make this concise and readable.

    \subsubsection*{Task C -- Users with a Chosen Hobby}
    \textbf{Pig idea:} filter only; no group and no join.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Loaded pages.
        \item Filtered by hobby parameter \texttt{\$HOBBY} (case-insensitive).
        \item Projected only nickname and jobtitle.
    \end{itemize}

    \textbf{Important note from Project 1 comment:}
    In MapReduce this should be map-only. In Pig, this script is also filter/projection style with no explicit reduce-style grouping stage, which matches that idea.

    \subsubsection*{Task D -- Popularity Factor (followers per owner, including zero)}
    \textbf{Pig idea:} compute follower counts by followed user (ID2), then left join with all page owners.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Built owner list from CircleNetPage.
        \item Grouped follows by \texttt{id2} and counted followers.
        \item Left-outer joined owners with counts and replaced null with zero.
    \end{itemize}

    \textbf{Why this design:}
    This keeps all owners, including owners with no followers, and avoids the single-cache-file assumption noted in Project 1 feedback.

    \subsubsection*{Task E -- Total Actions and Distinct Pages Accessed}
    \textbf{Pig idea:} group actions by user, count total events, and count distinct pages.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Grouped ActivityLog by \texttt{bywho}.
        \item Used \texttt{COUNT(actions)} for total actions.
        \item Used \texttt{DISTINCT actions.page\_id} then \texttt{COUNT(...)} for distinct pages.
        \item Left joined with full owners list so all page owners appear.
    \end{itemize}

    \textbf{Why this design:}
    Pig nested block in \texttt{FOREACH ... \{ ... \}} is a clean way to compute both metrics together.

    \subsubsection*{Task F -- Owners Above Average Follower Count}
    \textbf{Pig idea:} compute owner follower counts (with zero-filled owners), compute global average, then filter owners above average.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Reused owner follower count flow from Task D.
        \item Computed global average using \texttt{GROUP ... ALL} + \texttt{AVG(...)}.
        \item Used \texttt{CROSS} to attach average to each owner and filtered \texttt{followers > avg}.
    \end{itemize}

    \textbf{Why this design:}
    This avoids reading a single reducer part file manually and keeps average calculation in Pig pipeline logic.

    \subsubsection*{Task G -- Outdated Pages (No Access in Last 90 Days)}
    \textbf{Pig idea:} compute per-user latest activity and global latest activity, then compare against threshold \texttt{global\_max - 2160}.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Built per-user max action time with \texttt{GROUP by user} + \texttt{MAX}.
        \item Built global max action time with \texttt{GROUP ALL} + \texttt{MAX}.
        \item Left joined users to per-user max and crossed with global max.
        \item Filtered users with null last-time or older-than-threshold last-time.
    \end{itemize}

    \textbf{Why this design:}
    Everything stays in relational flow and does not depend on one output part file.

    \subsubsection*{Task H -- Same-Region One-Way Follows (Not Followed Back)}
    \textbf{Pig idea:} join follows with region table for both source and destination, keep same-region edges, detect non-reciprocal edges, then attach nickname.

    \textbf{How We implemented it:}
    \begin{itemize}
        \item Joined follows with page-region table on source and destination.
        \item Filtered only same-region edges and removed self loops.
        \item Built reversed edge relation and left-outer joined to detect missing reverse edges.
        \item Selected unique source users and joined with page table for nickname.
    \end{itemize}

    \textbf{Why this design:}
    We used reduce-side relational joins instead of loading all pages into memory cache, which directly addresses the scalability concern from Project 1 feedback.

    \subsection{Trade-off Discussion: Apache Pig vs Standard MapReduce}

    \subsubsection*{Where Pig helped}
    \begin{itemize}
        \item Much faster development for relational tasks (load/filter/group/join/order).
        \item Scripts are shorter and easier to read than Java MapReduce jobs.
        \item Good for iteration and analytics workflow where readability is important.
    \end{itemize}

    \subsubsection*{Where MapReduce helped}
    \begin{itemize}
        \item Better performance in this project after optimization.
        \item Finer control over execution details (combiner use, map-only design, stage control).
        \item Easier to tune task-specific logic for runtime improvement.
    \end{itemize}

    \section{Task 2: K-means with Hadoop MapReduce}
    For Task 2, we implemented K-means in Java MapReduce using one main driver (\texttt{KMeansMain}) and mode-based behavior. We kept the code structure simple: same core mapper/reducer logic, different iteration control and output strategy by mode.

    \subsection{What We Implemented (2a--2e)}
    {\small
    \begin{longtable}{@{}p{0.25\linewidth}p{0.14\linewidth}p{0.27\linewidth}p{0.24\linewidth}@{}}
        \toprule
        Requirement & Mode & What changes & Main output \\
        \midrule
        2(a) Single iteration & \texttt{SINGLE} & Force \(R=1\) & centers + summary \\
        2(b) Basic multi-iteration & \texttt{BASIC} & Run fixed \(R\), no early stop & centers + summary \\
        2(c) Early stop & \texttt{EARLY} & Stop by threshold (\texttt{epsilon}/\texttt{sse.epsilon}) & centers + summary \\
        2(d) Optimized MR & \texttt{OPT\_CENTERS} & Combiner enabled & centers + summary \\
        2(e)(ii) Points output & \texttt{OPT\_POINTS} & Final assignment job & centers + points with cluster \\
        \bottomrule
    \end{longtable}
    \normalsize}

    Mapper/reducer behavior is the same base across modes: mapper assigns each point to nearest center, reducer recomputes centers by averaging assigned points. In optimized modes we enable the combiner to reduce shuffle data.

    \subsubsection*{SSE and Convergence}
    We used two types of evidence:
    \begin{itemize}
        \item \texttt{summary.txt}: final SSE, converged flag, rounds executed
        \item \texttt{metrics.csv}: per-iteration shift, SSE, delta\_SSE
    \end{itemize}
    This made it clear that the algorithm is working even when a run does not hit convergence within the round budget.

    Baseline SSE trend (K=5) from our previous runs:
    \begin{itemize}
        \item SINGLE (R=1): \(8.0020\times10^{13}\)
        \item BASIC (R=10): \(5.0990\times10^{13}\)
        \item OPT\_CENTERS (R=30): \(4.9431\times10^{13}\)
    \end{itemize}
    So the objective keeps improving with more rounds.

    \subsubsection*{Scaling Check (BASIC vs OPT\_CENTERS)}
    From \texttt{task2\_report\_artifacts\_plus/tables/scaling\_table.csv}:
    \begin{longtable}{@{}lrr@{}}

    In our runs with larger input size, the optimized mode (\texttt{OPT\_CENTERS}) was faster. The main reason is that the combiner does local partial aggregation before shuffle, so less intermediate data is transferred to reducers.

    \subsubsection*{Team Conclusion}
    Based on our experiments, \texttt{OPT\_CENTERS} was the most practical default for this project setup. It includes combiner optimization, gives compact output (\texttt{final\_centers.csv} + \texttt{summary.txt}), and remained competitive in runtime across the tested settings. We also learned that matching \(K\) with the seed file is important for valid K-wise SSE comparison.
